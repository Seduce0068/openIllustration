## ADR-0002: JPKI認証連携方式

- Status: Accepted
- Date: 2026-11-02
- Approved: 2026-11-02（プロジェクトオーナーの包括委任）
- Decision owners: Project owner
- Scope: 本番の利用資格判定に用いる認証方式

## Context

要件は、指定マイナアプリ/JPKI認証をサイト利用資格の必須条件とし、
認証できない利用者にコンテンツ閲覧を含む機能を提供しないことである。
現行実装は開発用モックであり、X.509証明書から公開鍵を抽出するだけで、
発行元、署名、nonce、失効、属性を検証していない。

デジタル庁は「デジタル認証サービス」を提供している。これはマイナアプリと
連携し、OAuth 2.0 / OpenID Connect の認可コードフローで認証・署名を行う
公式APIである。2026年夏にデジタル認証アプリはマイナアプリへ統合された。
民間事業者は申込とクライアントIDの発行を受け、リダイレクトURIを登録する
必要がある。技術仕様の入手から主務大臣認定まで6か月から1年程度を要する
と案内されている。

## Decision

以下を提案する。承認後に Status を Accepted へ変更する。

1. **認証基盤**: デジタル庁のデジタル認証サービスを採用する。
   J-LISの技術仕様書を直接入手してカードAPライブラリを自前実装する方式は
   採用しない。ブラウザ・OS依存と認定負担が大きいためである。
2. **フロー**: BFF（Backend For Frontend）を置き、OIDC認可コードフロー、
   PKCE、`state`、`nonce` を用いる。ブラウザにトークンを保持しない。
   BFFは `state`、`nonce`、`code_verifier` をサーバー側の短寿命ストアに
   保持し、ブラウザとはHttpOnlyの結合Cookieで紐付ける。コールバック時に
   一度だけ消費し、期限切れ・再利用・不一致を拒否する。
3. **認証と属性**: ログインには利用者証明用電子証明書を使う。
   利用資格判定に必要な生年月日と居住地域のみをUserInfoから取得する。
   氏名・性別は取得しない。追加属性が必要になった場合は、目的と保持期間を
   ADRで定める。署名用電子証明書は、投稿署名など別途必要な操作に限って使う。
   認証保証レベルは、利用者証明用電子証明書による認証を要求し、
   IDトークンまたはメタデータで `acr` / `amr` が提供される場合は
   要求値との一致を確認する。提供されない場合の識別方法は
   Open Questions とし、確認できるまで本番有効化しない。
4. **IDトークン検証**: 次を必須とする。
   - JWK Setを取得し、`kid` を照合する。鍵は `kid` ごとに
     `Cache-Control` に従ってキャッシュし、未知の `kid` は
     一度だけ再取得する。取得失敗時は認証を失敗させる。
   - `alg` が `ES256` であることを確認する。
   - 署名を検証する。
   - `iss` がOpenID Providerメタデータの `issuer` と一致する。
   - `aud` にクライアントIDが含まれる。
   - `exp` が現在時刻より未来である。
   - `nbf` が現在時刻以前である。
   - `iat` が許容範囲内である。
   - `auth_time` が許容範囲内で、必要な場合は `max_age` を要求する。
   - `nonce` が認可リクエストで発行した値と一致する。
   - `at_hash` がアクセストークンと一致する。
5. **利用者識別**: IDトークンの `sub`（PPID）を `user_hash` として使う。
   クライアントが申告するIDや生年月日を主体の根拠にしない。
   PPIDはRPごとにユニークであり、他サービスと相関しない。
6. **セッション**: 検証済みの認証トランザクションに結び付けた短寿命JWTを
   サーバーで発行し、HttpOnly・Secure・SameSiteのCookieで保持する。
   JWTには `sid` を含め、サーバー側の失効状態を全リクエストで照合する。
   リフレッシュトークンはハッシュ化してサーバー側に保存し、使用ごとに
   ローテーションする。旧トークンの再提示を検知した場合は、当該利用者の
   全セッションを無効化する。現行のHS256 JWTは移行期間中のみ併存させ、
   BFF Cookieを正とする。移行完了後に新規発行を停止し、既存トークンは
   `exp` と鍵ローテーションで失効させる。二重検証を恒久化しない。
7. **年齢・地域**: UserInfoの生年月日と居住地域、別途確定する対象地域
   ポリシーで判定する。生年月日と居住地域は取得後1時間以内に削除する。
   長期保持するのは `ppid`、`age_verified_at`、`threshold`、
   `policy_version`、`verification_method` に限る。監査証跡には
   個人属性を含めない。
8. **ログアウト**: back-channel logoutを受け、該当セッションを無効化する。
   logoutトークンの `iss`、`aud`、`sub`、`sid`、`events`、`exp`、`iat`、
   署名を検証する。`jti` を記録して単回性を確認し、再送を拒否する。
   `sid` が一致するセッションのみを無効化する。
9. **開発・試験**: デジタル認証サービスのテストカード代替機能を使う。
   `ALLOW_MOCK_AUTH` は引き続き開発専用とし、本番では起動時に無効化する。
10. **移行**: 実装前にクライアントID、リダイレクトURI、JWK Set、
    テスト環境の利用可否を確認する。モック由来の `user_hash` は
    本番へ引き継がず、テストデータのみを対象に破棄する。本番有効化は、
    申込・認定・実機試験・運用承認の完了後とする。

## 実装状況（2026-11-02）

- `/auth/oidc/start` と `/auth/oidc/callback` を実装した。
- state、nonce、code_verifier はサーバー側に10分間保存し、state は単回消費する。
- IDトークンはJWKSの `kid` でES256署名を検証し、`iss`、`aud`、`exp`、
  `nbf`、`iat`、`nonce`、`at_hash` を確認する。
- `sub`（PPID）を `user_hash` としてセッションJWTとHttpOnly Cookieに結合する。
  ログアウト時と back-channel logout 時に `sid` を失効させ、以後のJWTを拒否する。
- テストはローカルOPモックで、正常系・state再利用・nonce不一致・
  ログアウト失効・back-channel logout を検証する。
- 未実装: `acr`/`amr`、`auth_time`/`max_age`、`sub` 単位の全セッション失効、
  リフレッシュトークン、実サービス接続、事業者申込。

## Consequences

- 認証の信頼根拠をJ-LISとデジタル認証サービスに置く。自前の証明書検証を
  最小化できる一方、外部サービスの可用性・仕様変更に依存する。
- BFFはOIDCクライアントとセッションを、APIは認可とドメイン検証を担う。
  年齢判定・主体識別の規則は `common` に置き、BFFへ漏らさない。
- PPIDにより利用者の相関を抑えられるが、アカウント削除・再登録時の
  同一性判定は別途設計が必要である。
- UserInfoの属性は1時間以内に削除する必要があり、長期保持しない。
- 本番導入には民間事業者向け申込と認定が必要で、リードタイムが長い。
- 決済・監査の主体識別はPPIDに統一し、クライアント申告IDを排除する。
- クライアントシークレット、セッションJWTの署名鍵、リフレッシュトークンは
  秘密管理ストアに置き、`kid` 付きでローテーションする。漏えい時は
  該当鍵の失効と全セッションの無効化を行う。

## Alternatives

- **J-LIS技術仕様書の直接入手と自前実装**: カードAPライブラリ、証明書
  パス、CRL/OCSP、nonce結合を自前で実装する。制御性は高いが、認定・
  実機対応・保守の負担が大きく、本プロトタイプの規模に合わない。
- **OID4VPの直接実装**: 標準仕様に沿うが、マイナアプリの対応状況、
  提示形式、信頼リストの運用が未確認である。
- **モック認証の継続**: 本番の利用資格判定を満たさないため採用しない。

## Open Questions

- 対象地域、年齢閾値、必要な属性、保持期間の法務レビュー。
- `acr` / `amr` の提供有無と要求値。提供されない場合の保証レベル識別。
- PPIDのローテーション、アカウント削除、再登録の扱い。
- リフレッシュトークンの保存先と失効伝播。
- デジタル認証サービスの利用条件、審査、費用、SLA。
- 投稿署名に署名用電子証明書を必須とするか、認証済みセッションで
  代替するか。
- 追加の認証保証レベルや属性を追加する際の受入基準。
