# ADR-0003: JPYC決済方式

- Status: Proposed
- Date: 2026-11-02
- Decision owners: Project owner
- Scope: 有償取引・支援の決済と送金検証

## Context

要件は、プラットフォーム内の有償取引・支援にJPYCのみを用い、
許可チェーン・許可コントラクト上の送金を検証した後だけ有償機能を
解放することである。現行の支援APIは501で無効化されており、
模擬取引記録は支払証明にならない。

2026年11月時点のJPYC株式会社の公表資料では、JPYCは資金移動業の
電子決済手段であり、Ethereum、Polygon、Avalanche C-Chain、Kaiaの
4チェーンで発行される。現行コントラクトは4チェーンで共通の
プロキシアドレス `0xE7C3D8C9a439feDe00D2600032D5dB0Be71C3c29` と
案内されている。旧JPYC Prepaidの `0x431D5dfF03120AFA4bDf332c61A6e1766eF37BDB`
とは別コントラクトであり、混同してはならない。

発行・償還の1回上限は100万円、下限は3,000円である。償還時の
ブロック承認回数は、Ethereum 32、Avalanche C-Chain 12、
Polygon 256、Kaia 12と公表されている。

## Decision

以下を提案する。承認後に Status を Accepted へ変更する。

1. **対応チェーン**: 次の4チェーンをallowlistに登録する。
   - Ethereum Mainnet: chain ID `1`
   - Polygon: chain ID `137`
   - Avalanche C-Chain: chain ID `43114`
   - Kaia Mainnet: chain ID `8217`
2. **トークン識別**: chain IDとトークンコントラクトの組で識別する。
   コントラクトはプロキシアドレス `0xE7C3D8C9a439feDe00D2600032D5dB0Be71C3c29`
   を登録し、実装アドレスや旧Prepaidを許可しない。allowlistは設定ファイル
   ではなく、監査可能なコードまたはDBで管理する。
3. **決済フロー**:
   1. サーバーが注文ID、金額、chain ID、受取アドレス、有効期限を発行する。
   2. 利用者がウォレットからJPYCを送金する。
   3. サーバーがトランザクションを取得し、検証する。
   4. 必要確認数に達した後、注文を確定し、有償機能を解放する。
   5. 失敗・期限切れ・確認中の状態を区別して記録する。
4. **検証項目**:
   - `chain_id` がallowlistと一致する。
   - `to` がトークンコントラクトで、`Transfer` の受取先が注文の受取先と一致する。
   - 送金元が注文を作成した利用者のウォレットと一致する。
   - 金額が注文と一致し、小数桁を誤解釈しない。
   - トランザクションが成功し、必要な確認数に達している。
   - 同一 `tx_hash` を二重使用できない（DBの一意制約）。
5. **最終性**: 償還時の承認回数を初期値とし、チェーンごとに設定可能に
   する。Ethereum 32、Avalanche 12、Polygon 256、Kaia 12。
   Polygonの256確認は長時間を要するため、UXとリスクの許容範囲を
   別途決定する。
6. **金額**: 1回100万円以下を上限とする。プラットフォーム内の
   取引上限・支援上限は別途決定する。送金手数料は利用者負担とし、
   送金前に見積りを表示する。
7. **返金・紛争**: 自動返金は実装しない。手動対応のRunbook、証跡、
   返金時の本人確認を整備するまで、返金を約束する表示をしない。
8. **RPC**: 複数のRPCプロバイダを使い、失敗時に切り替える。
   取得したトランザクション・レシート・ブロック番号を監査ログに残す。
9. **監査**: 注文作成、送金検出、確認数到達、確定、失敗、返金を
   監査対象イベントとし、第三者が検証できる形式へ移行する。

## Consequences

- チェーンごとの確認時間と手数料が異なり、UXが不均一になる。
- RPCプロバイダ、チェーン再編成、コントラクトのアップグレードに
  継続的に追随する必要がある。
- 旧Prepaidコントラクトや非対応チェーンへの送金は救済できない。
  送金先の表示と注意喚起を徹底する。
- 資金移動業・犯罪収益移転防止法・税務・会計の確認が必要である。
- 自動返金を行わない間は、失敗時の運用負担が残る。

## Alternatives

- **Polygonのみに限定**: 確認時間と運用は単純化できるが、利用者の
  チェーン選択を狭め、Kaia等の利用者を取り込めない。
- **決済代行サービスの利用**: カード等の代替決済を設けない方針と、
  JPYCのオンチェーン検証要件に反するため採用しない。
- **オフチェーン台帳のみ**: 送金の存在を第三者検証できず、要件を
  満たさないため採用しない。

## Open Questions

- RPCプロバイダの選定とSLA、複数プロバイダ間の整合性確認。
- Polygon 256確認の待ち時間を許容するか、別の最終性基準を設けるか。
- 手数料の負担方法と表示方法。
- 返金・紛争・誤送金の運用と法的位置づけ。
- 税務・会計上の処理と帳票。
- コントラクトのアップグレード・停止（pause）時の扱い。
