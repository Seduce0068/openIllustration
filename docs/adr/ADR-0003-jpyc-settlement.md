## ADR-0003: JPYC決済方式

- Status: Accepted
- Date: 2026-11-02
- Approved: 2026-11-02（プロジェクトオーナーの包括委任）
- Decision owners: Project owner
- Scope: 有償取引・支援の決済と送金検証

## Context

要件は、プラットフォーム内の有償取引・支援にJPYCのみを用い、
許可チェーン・許可コントラクト上の送金を検証した後だけ有償機能を
解放することである。現行の支援APIは501で無効化されており、
模擬取引記録は支払証明にならない。

2026年11月時点のJPYC株式会社の公表資料では、JPYCは資金移動業の
電子決済手段であり、Ethereum、Polygon、Avalanche C-Chain、Kaiaの
4チェーンで発行される。現行コントラクトは4チェーンで共通の
プロキシアドレス `0xE7C3D8C9a439feDe00D2600032D5dB0Be71C3c29` と
案内されている。旧JPYC Prepaidの `0x431D5dfF03120AFA4bDf332c61A6e1766eF37BDB`
とは別コントラクトであり、混同してはならない。

発行・償還の1回上限は100万円、下限は3,000円である。償還時の
ブロック承認回数は、Ethereum 32、Avalanche C-Chain 12、
Polygon 256、Kaia 12と公表されている。

## Decision

以下を提案する。承認後に Status を Accepted へ変更する。

1. **対応チェーン**: 次の4チェーンをallowlistに登録する。
   - Ethereum Mainnet: chain ID `1`
   - Polygon: chain ID `137`
   - Avalanche C-Chain: chain ID `43114`
   - Kaia Mainnet: chain ID `8217`
2. **トークン識別**: chain IDとトークンコントラクトの組で識別する。
   コントラクトはプロキシアドレス `0xE7C3D8C9a439feDe00D2600032D5dB0Be71C3c29`
   を登録し、実装アドレスや旧Prepaidを許可しない。allowlistはコード定数
   として管理し、変更はADRとマイグレーションを伴う。更新権限、承認者、
   緊急delist手順をDEC-03の完了条件に含める。
3. **注文とウォレットの結合**:
   1. サーバーが注文ID、金額、chain ID、注文ごとの受取アドレス、
      有効期限、利用者のPPIDを記録する。注文IDは128bit以上の
      CSPRNG（UUIDv4またはULID）で生成し、DBで一意制約を課す。
   2. 利用者は注文IDとnonceに対するウォレット署名を送り、サーバーが
      署名者アドレスを検証する。署名者アドレスを `wallet_address` として
      注文に結合する。以後、別アドレスからの送金は受理しない。
   3. 利用者がウォレットから受取アドレスへJPYCを送金する。
   4. サーバーがトランザクションを取得し、検証する。
   5. 必要確認数に達した後、注文を確定し、有償機能を解放する。
4. **受取アドレスと鍵管理**: 注文ごとにHDウォレットから一意の受取
   アドレスを派生し、注文と1:1で紐付ける。共有アドレス方式は、同一送金元・
   同一金額の注文をオンチェーンで区別できないため採用しない。
   マスターシードはHSMまたは複数名の承認を要するマルチシグで管理し、
   単一運用者に依存しない。バックアップ・復旧・鍵ローテーションを
   Runbook化する。
5. **検証項目**:
   - `chain_id` がallowlistと一致する。
   - トランザクションが成功し、`status == 1` である。
   - レシートの `logs[N].address` がallowlistのコントラクトと一致する。
   - `Transfer` ログの `removed` が `false` である。
   - `to` が注文の受取アドレスと一致する。
   - `from` が注文に結合した `wallet_address` と一致する。
   - `value` が注文金額と一致する。比較前にコントラクトの `decimals()` を
     取得し、最小単位の整数（u128）で比較する。浮動小数は使わない。
     100万円×10^18 は u128 の範囲内だが、`i64` では扱わない。
   - `(chain_id, tx_hash, log_index)` が一意である。
   - 必要な確認数に達している。
6. **状態機械**: 注文は次の状態を取る。
   - `PENDING`: 注文作成、送金待ち。既定30分で `EXPIRED`。
   - `DETECTED`: トランザクション検出。
   - `CONFIRMING`: 確認数待ち。確認数到達後に親ハッシュとブロック番号を
     再取得し、再編成を検知した場合は `DETECTED` へ戻す。
   - `FINALIZED`: 確定。有償機能を解放する。
   - `FAILED`: 送金失敗（revert）または検証不能。
   - `MISMATCH`: 金額・送金元・受取先の不一致。自動確定しない。
   - `EXPIRED`: 期限切れ。送金済みの場合は手動対応。
   部分支払・過払・期限後送金は `MISMATCH` として手動対応し、
   自動返金しない。
7. **最終性**: 償還時の承認回数を初期値とし、チェーンごとに設定可能に
   する。Ethereum 32、Avalanche 12、Polygon 256、Kaia 12。
   Polygonの256確認は長時間を要するため、UXとリスクの許容範囲を
   別途決定する。
8. **金額**: 1回100万円以下を上限とする。プラットフォーム内の
   取引上限・支援上限は別途決定する。送金手数料は利用者負担とし、
   送金前に見積りを表示する。
9. **RPCとコントラクト監視**: 複数のRPCプロバイダを使い、2-of-3の一致を
   確認する。不一致時は `CONFIRMING` に留めてアラートを出し、自動確定しない。
   最新ブロックのタイムスタンプが古い場合はstaleとして扱う。コントラクトの
   実装アドレスと `pause` 状態を定期監視し、変更を検知した場合は検証を
   一時停止してアラートを出す。取得したトランザクション・レシート・
   ブロック番号を監査ログに残す。
10. **監査**: 注文作成、ウォレット結合、送金検出、確認数到達、確定、
    失敗、返金を監査対象イベントとする。各イベントに `chain_id`、
    `tx_hash`、`log_index`、`block_number`、`confirmations` を含め、
    第三者が検証できる形式へ移行する。

## 実装状況（2026-11-02）

- 注文作成、ウォレット所有証明（EIP-191）、検証インターフェース、
  状態機械を実装した。
- `PAYMENT_RECEIVING_XPRV` を設定した場合、注文ごとに BIP44
  (`m/44'/60'/0'/0/{index}`) で受取アドレスを派生する。未設定時は
  `PAYMENT_RECEIVING_ADDRESS` の単一アドレスを使う。
- RPC検証と2-of-3クォーラムは未実装。`PaymentVerifier` の本番実装を
  追加するまで検証APIは501を返す。
- バックグラウンドの確認ワーカー、返金、AML/KYCは未実装。

## Consequences

- 注文ごとのアドレス派生とマスターシードの管理が必要になり、
  鍵運用の設計・訓練・監査が必須になる。
- チェーンごとの確認時間と手数料が異なり、UXが不均一になる。
- RPCプロバイダ、チェーン再編成、コントラクトのアップグレードに
  継続的に追随する必要がある。
- 旧Prepaidコントラクトや非対応チェーンへの送金は救済できない。
  送金先の表示と注意喚起を徹底する。
- 資金移動業・犯罪収益移転防止法・税務・会計の確認が必要である。
  本人確認、疑わしい取引の届出、取引記録の保存期間と主体は、
  後続ADRで具体化するまで本番有効化しない。
- 自動返金を行わない間は、失敗時の運用負担が残る。

## Alternatives

- **共有受取アドレス**: 注文ごとの識別ができず、同一送金元・同一金額の
  照合が曖昧になるため採用しない。
- **Polygonのみに限定**: 確認時間と運用は単純化できるが、利用者の
  チェーン選択を狭め、Kaia等の利用者を取り込めない。
- **決済代行サービスの利用**: カード等の代替決済を設けない方針と、
  JPYCのオンチェーン検証要件に反するため採用しない。
- **オフチェーン台帳のみ**: 送金の存在を第三者検証できず、要件を
  満たさないため採用しない。

## Open Questions

- HDウォレットのマスターシードの保管方法（HSM/マルチシグの構成、
  承認者、バックアップ）。
- RPCプロバイダの選定とSLA、2-of-3の裁定規則の詳細。
- Polygon 256確認の待ち時間を許容するか、別の最終性基準を設けるか。
- 手数料の負担方法と表示方法。
- 返金・紛争・誤送金の運用と法的位置づけ。
- 税務・会計上の処理と帳票。
- 本人確認、疑わしい取引の届出、取引記録の保存期間と主体。
- コントラクトのアップグレード・停止（pause）時の扱い。
- 追加チェーンをallowlistへ加える際の受入基準。
