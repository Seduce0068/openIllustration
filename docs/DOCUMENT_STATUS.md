# 文書・設計判断の確定状況

## 結論

プロダクトの必須方針は確定しているが、設計文書全体は最終確定していない。
文書は目標・現行実装・未決事項を区別したレビュー可能な状態であり、
本番要件の方式や受け入れ値には未決定事項が残る。

## 確定している方針

- OSSとして開発し、反検閲性、高速・軽量、クロスプラットフォーム性、
  利用者の低負担を目指す。
- 指定されたマイナアプリ/JPKI認証をサイト利用資格の必須条件とし、コンテンツ閲覧を含む未認証利用を認めない。認証開始とhealth確認は限定的な例外とする。
- 有償取引・支援にはJPYCのみを使う。閲覧だけにJPYC保有は要求しない。
- 重要操作は第三者が検証可能な監査設計とする。
- Rustを優先し、バックエンドはAxumを基準とする。
- 実装されていない機能を実装済み・本番対応済みとして扱わない。
- 年齢/地域ポリシーの**有効設定値**（しきい値・国別上書き・対象地域・適用モード等の非秘密情報）は常に公開する（`GET /policy/age`）。秘密情報（鍵・トークン・認証情報等）は公開しない。

## エージェント推奨案と採用判断（2026-11-16）

プロジェクトオーナーの包括委任に基づき、リポジトリ内で吟味した推奨案を採用した。
**いずれも法的適合の確定主張ではなく、外部サービス接続・実機検証・専門家レビューを
代替しない。** 外部条件の成立後に再評価する。

### 吟味の判断基準

以下の基準で代替案を比較し、後戻り可能性が高く外部依存が少ない案を優先した。

1. **フェイルクローズ優先**: 設定不足・検証不能時は拒否側へ倒す。
   自動承認・自動BAN・モック本番利用など、誤った through を許す案は採用しない。
2. **確定主張の回避**: 法的事実・監査完全性・本番適合を実装や文書だけで
   確定させない。「変更検知」と「第三者検証可能な監査」を区別する。
3. **外部依存の最小化**: 実サービス接続・実機試験・専門家レビューを要する
   判断は、その条件を未了として明示し、先に進められる方針だけを採用する。
4. **現行実装との連続性**: 既存の実装・テスト・設定を壊さず、採用した方針との
   差分（未実装項目）を正直に記録する。
5. **可逆性**: 後から厳しくできる案（未測定の数値を確定しない、
   `acr`/`amr` 未提供時は有効化しない等）を選ぶ。

代替案の検討結果（代表例）:

- **ADR-0004**: 3票即時確定・同数 `Approved` は、反対意見の機会がなく
  公開継続リスクが残るため不採用。7日間の投票期間＋同数 `Rejected` を採用
  （[ADR-0004](adr/ADR-0004-moderation-procedure.md) の Alternatives 参照）。
- **DEC-04**: DB内ハッシュ連鎖を第三者検証可能な監査とみなす案は不採用。
  変更検知として扱い、別ADR策定を本番ゲートとして残す。
- **DEC-07**: 未測定の受入値を先に数値確定する案は不採用。測定条件を固定し、
  数値は実測後に決定する。
- **DEC-08**: マルチリージョン／マルチライター構成は初期運用として
  複雑すぎるため不採用。単一ライター＋TLS終端を採用し、
  必要になった時点でスケールアウトを別設計で検討する。

## 現行文書の扱い

- [ADR-0001](adr/ADR-0001-mvp-trust-boundaries.md) はプロダクト原則を承認する。
  個別の認証、決済、監査、運用方式まで承認したものではない。
- 要件・設計文書は要求と目標設計を記録する。未実装箇所は
  [詳細設計書](DETAILED_DESIGN.md) と [テスト仕様書](TEST_SPECIFICATION.md)
  の状態表記を優先する。
- 本番化前に未決定項目をすべて解消し、実装、試験、運用承認の証跡を残す。
