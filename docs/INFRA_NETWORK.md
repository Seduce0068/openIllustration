## インフラ・ネットワーク設計（MVPの制約）

## 1. 現行実装

- AxumサーバーはIPv6 unspecified address (`[::]:3000`) にbindする。
- `network::ipv6_only_middleware` は接続元IPv4を拒否する。ただし `ALLOW_IPV4_LOCALHOST=1` の場合はIPv4ループバックを許可する。
- クライアントIPの判定は実際のピアアドレスを既定とする。IPv4-mapped IPv6（`::ffff:a.b.c.d`）は dual-stack バインドの IPv4 接続を表すため IPv4 として正規化する。
  `TRUSTED_PROXY_CIDRS`（カンマ区切りの IP / CIDR）に含まれるピアからのみ `X-Forwarded-For` の末尾値（信頼済みプロキシが追記・上書きした値）を採用し、信頼済みピアで解決できない場合は
  403 とする（fail-closed）。未設定時はピアアドレスのみで判定する（NET-02）。
- 拒否時は理由（IPv4 ゲート / 信頼済みプロキシの解決不能）をログに記録する。IPv4 拒否は debug、解決不能は warn とし、IPアドレスは記録しない。
- CORSはローカル開発用の3 originに限定している。本番フロントエンドのoriginは未設定。

## 2. 設計上の注意

- IPv6限定は認証・認可・ボット対策の代替ではなく、ゼロトラストや個人識別を保証しない。
- プロキシ配下では `TRUSTED_PROXY_CIDRS` に信頼済みプロキシの範囲のみを設定し、プロキシ側は自身が観測したピアアドレスを `X-Forwarded-For` に上書きまたは追記する構成にする。
  先頭値はクライアントが注入できるため判定に使わず、信頼範囲を設定できない場合は本ヘッダーを使わない。単一のリバースプロキシ（隣接 1 ホップ）を前提とし、多段構成は別途設計する。全アドレスを含む範囲（プレフィックス長
  0）と不正な要素は起動時に警告のうえ無視する。範囲は IPv4 / IPv6 の正規形で指定する（v4-mapped 表記の CIDR は受理しない）。
- プロキシで `real_ip_header` 等により `$remote_addr` をクライアント供給ヘッダから再定義する構成は、`set_real_ip_from` の範囲を信頼済みホップだけに限定する。
  限定できない場合は本ヘッダーを判定に使わない。
- 信頼済みピアからの `X-Forwarded-For` なしリクエストは 403（fail-closed）となる。liveness/readiness プローブ、監視、内部呼び出しの経路は、信頼範囲外からの実行・プロキシでの XFF
  付与・`/health` の扱い分離のいずれかを本番インフラ確定時に決定する（§3.4）。
- IPv4拒否を製品要件として維持するか、ネットワーク層のアクセス制御に置くかは本番インフラ確定時に決定する。IPv6利用者への影響と運用コストを評価する。
- Cloudflare/OpenTofuの設定例は現行リポジトリにデプロイ可能なIaCとして存在しない。IPv6有効化とIPv4遮断は別要件として検証する。

## 3. 本番化に必要な決定

1. TLS終端、公開ポート、リバースプロキシ構成。
2. クライアントIPを必要とする機能と、信頼済みプロキシ範囲。
3. 本番CORS originと許可メソッド・ヘッダー。
4. IPv6/IPv4ポリシー、ヘルスチェック経路、ファイアウォール/WAFルール。
5. 設定のIaC化、ステージング検証、ロールバック手順。
