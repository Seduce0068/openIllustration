# 要件仕様書 (Requirements Specification)

本書は[要求定義書](REQUIREMENTS_DEFINITION.md)と
[ADR-0001](adr/ADR-0001-mvp-trust-boundaries.md)に基づく必須要件を定める。
要件が未実装の場合は未実装と明記し、任意要件へ読み替えない。

## 1. 機能要件

### 1.1 本人確認・利用資格

- 指定されたマイナアプリ/JPKIによる認証をサイト利用資格の必須条件とする。
- 認証できない利用者には、コンテンツ閲覧を含むサイト機能を提供しない。公開読み取りAPIも認証境界の対象とする。認証開始に必要なエンドポイント、静的ログイン画面、運用ヘルスチェックのみを例外として許容し、コンテンツ・個人データを返してはならない。
- バックエンドは提示の署名、nonceとの結合、発行元・証明書の信頼性、失効状態、audience等の仕様対象を検証する。詳細プロトコルは公式仕様に基づき決定する。
- 認証成功後のセッション/JWTは検証済み認証トランザクションに暗号学的に結び付ける。クライアント提供の識別子だけで利用者主体を決定しない。
- 生年月日等の属性を取得する場合は必要最小限とし、確認結果と生データの保存要否・期間を明示する。
- 開発用モックは本番から分離し、未設定時に無効とする。モック認証中の環境で本番データ・本番決済を扱わない。

### 1.2 コンテンツ

- 対象はJPEG XL静止画とMarkdown小説。
- IPFS CID等のコンテンツアドレスと、アプリケーションのチェックサムを区別する。
- 投稿・取得・描画の各境界で署名・サイズ・形式・チェックサムを検証する。
- 単一ゲートウェイ停止・遮断時に代替配信経路を利用できる設計とする。
- 投稿者本人性、著作権、コンテンツ安全性はチェックサムだけで証明しない。

### 1.3 監査・モデレーション

- 投稿、本人確認結果、通報、投票、状態変更等の重要操作を監査対象として定義する。
- 監査記録は運営者以外が検証できる完全性・順序性を備える。DB内ハッシュ連鎖だけを最終要件の達成とみなさない。
- モデレーションは通報、暫定非表示、判定、通知、異議申立て、再審査の手続を定義する。
- 監査データの公開範囲は個人情報保護と検証可能性の両方を満たすよう設計する。

### 1.4 決済

- プラットフォーム内の有償取引・支援はJPYCを必須の決済手段とする。他の決済手段は提供しない。
- JPYC対応チェーン、トークン識別、送金先確認、トランザクション検証、最終性、手数料表示、失敗・返金・紛争処理を仕様化する。
- 有償機能の解放は、許可されたチェーン上の許可されたJPYCコントラクトからの、対象取引に結び付いた送金を検証した後に限る。
- 閲覧のみの利用にJPYC保有を要求するものではない。
- 取引を実装するまで、模擬ハッシュやDB記録を実決済済みとして表示しない。

## 2. 非機能要件

### 2.1 OSS・Rust優先

- バックエンドはRust/Axumを基準とし、共有ロジック、クライアント、運用ツールもRustを優先する。
- 非Rust技術を採用する場合は、公式仕様適合、性能、保守性等の理由を記録する。
- ライセンス、ビルド手順、設定、データ移行、セルフホスト手順を公開する。
- Web標準を基本とし、主要機能を複数OS・端末・ブラウザから利用可能にする。対応環境と最小バージョンは利用者層と実機試験に基づき定義する。
- ブラウザごとの差がある画像デコード、JPKIアプリ連携、ウォレット接続は機能検出を行い、利用不能時は理由と代替手段を示す。セキュリティ必須条件をクライアント側フォールバックで迂回させない。

### 2.2 反検閲・可用性

- 配信・保存・名前解決の単一障害点とサービス停止権限を脅威モデル化する。
- 複数ゲートウェイ/ピン留め/ミラー等の選択肢と、データの更新・削除・通報手順を設計する。
- 反検閲性は違法コンテンツ対応や利用者の適正手続を省略する理由としない。

### 2.3 性能・コスト

- 高速・軽量・低手数料を目標とし、初期表示時間、配信量、Wasmサイズ、稼働費、取引手数料等の指標・測定環境・受入値を決定する。
- OS・ブラウザ・端末別の主要フロー完了率と描画互換性をクロスプラットフォーム受入基準として測定する。
- 具体的な数値目標は未決定であり、計測と合意なしに達成済みと主張しない。

## 3. 現行プロトタイプの制約

- 現行の固定mock login、X.509解析、DB内投票、模擬支援記録、単一DB監査連鎖は必須要件の完成実装ではない。
- JPKI、JPYC、外部検証可能な監査、分散配信を実装・試験・運用承認するまで、本番利用資格判定や実決済として有効化しない。
