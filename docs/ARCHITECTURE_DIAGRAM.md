## システム構成図 (System Architecture Diagram)

本書は必須要件を目指す論理構成と、現行プロトタイプとの差を分けて示す。
基本方針は [ADR-0001](adr/ADR-0001-mvp-trust-boundaries.md) を参照。

## 1. 目標構成（必須要件）

```text
[Browser / Rust-based client]
      │ HTTPS API
      ▼
[Rust / Axum API] ─────► [JPKI / 指定マイナアプリ検証]
      ├─────────────────► [JPYC対応チェーン・検証アダプタ]
      ├─────────────────► [検証可能な署名付き監査・外部アンカー]
      ├─────────────────► [libSQL / メタデータ]
      └─────────────────► [IPFS等の複数保存・配信経路]
```

ADR-0013 方針により実行時の機能検出は行わず、ビルド時フラグ（option_env!）で
  機能の有無を確定する。JXL/Wasmの描画機能がない環境では
安全な代替（対応形式のプレビュー、またはダウンロードと明確な案内）へ移る。
認証・決済の代替は認証・決済必須要件をスキップしてはならない。
プレビュー生成方式、チェーン、監査アンカー、JPKI連携API、
複数ストレージ事業者は未選定・未実装。図は目標構成であり、現在の接続を示さない。

## 2. 現行プロトタイプ

```text
[Leptos CSR / Rust-Wasm]
      ├─ JXL/Wasm利用可能 ──► Wasm描画
      └─ 非対応 ──────────► 代替表示/ダウンロード案内（方式未決定）
      │ HTTP API
      ▼
[Rust / Axum] ─────► [ローカル libSQL（file: 絶対パスのみ。リモート DSN は本番起動ゲートで拒否）]
      └─────────────► [Pinata API / IPFS gateways]
```

現行コードは開発時のみ有効な mock 認証（`ALLOW_MOCK_AUTH=1`）、本番向け OIDC/JPKI 経路
（state/nonce/PKCE、acr/amr、refresh）、DB内投票・監査記録、無効化済み支援APIを含む。
実JPKI認証、JPYC送金・確認、第三者検証可能な監査は完成していない。

## 3. 目標データフロー

1. **認証**: 指定マイナアプリで認証し、APIが信頼元・署名・nonce・必要属性を検証。成功時のみ認可トークンを発行する。
2. **投稿・配信**: APIが入力・署名・実データを検査し、複数経路で保存・配信する。CID、チェックサム、監査記録の役割を分離する。
3. **監査**: 重要イベントを署名付きで記録し、利用者または第三者が完全性・順序を検証できるようにする。
4. **モデレーション**: 通報・判断・異議申立てを追跡可能な状態機械として処理する。
5. **決済**: 有償取引はJPYCのみ。チェーン上の送金結果と最終性を検証して決済状態を確定する。

## 4. 信頼境界・制約

- **Client**: 利用者が制御する非信頼環境。クライアント側判定だけで認証・権利・決済を確定しない。
- **API**: Rust/Axumを基準に、認証後も各要求の認可・入力・署名を検証する。
- **JPKI**: 指定アプリ・信頼発行元・プロトコル仕様への依存を明示し、単なる証明書公開鍵抽出を本人確認としない。
- **JPYC**: 対象チェーン、コントラクト、最終性、トランザクション失敗・再編成を信頼モデルに含める。
- **監査**: DB内ハッシュ連鎖のみでは運営者改変への耐性や第三者検証を提供しない。
- **分散配信**: IPFSは利用可能性・削除不能性を保証しない。ピンニング、ゲートウェイ、ミラーと削除・通報手続きを併せて設計する。

## 5. 性能・運用目標

初期表示時間、API遅延、転送量、クライアントバンドルサイズ、配信可用性、インフラ費、JPYC手数料、OS/ブラウザ別の主要フロー完了率を測定する。対応環境マトリクス、SLO、目標値、測定環境は未決定で、達成済みとは主張しない。
