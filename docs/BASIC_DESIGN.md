## 基本設計書 (Basic Design Document)

本書は、反検閲・高速・軽量・低手数料のOSSサイトを実現する
基本方針を定める。必須方針と現行プロトタイプの差分は
[ADR-0001](adr/ADR-0001-mvp-trust-boundaries.md) を参照する。

## 1. プロダクト要件

- イラスト: JPEG XL静止画。
- 小説: Markdownテキスト。
- 指定マイナアプリ/JPKI認証を利用資格の必須条件とする。認証できない利用者には利用させない。
- プラットフォーム内の有償取引・支援にはJPYCのみを用いる。閲覧のみの利用にJPYC保有を求めるものではない。
- 重要操作を第三者が検証できる監査を備える。
- Rustを優先採用し、バックエンドはAxumを基準とする。
- Web標準を基本に複数OS・端末・ブラウザでの利用を目指す。Wasm/JXLを全環境で利用できるとは仮定しない。

## 2. 技術方針

- Backend: Rust / Axum。
- Shared logic: Rust (`common` crate)。認証検証、署名、チェックサム、監査形式等を責務ごとに分離する。
- Frontend: Rust / Leptos CSR / Wasmを基本候補とする。初期ロード・バンドルサイズ・主要ブラウザ互換性を測定し、JXLデコードやJPKI/ウォレット連携に代替経路を設ける。
- Database: 現行はlibSQL。監査情報の正本・公開性・削除要求への対応は本番方式を別途決める。
- Content storage: 現行はPinata経由のIPFS。最終設計では単一ピンニングサービス・ゲートウェイ依存を減らす。
- Payment: JPYC。対応チェーン・コントラクト・確認数・状態機械は [ADR-0003](adr/ADR-0003-jpyc-settlement.md) で決定。手数料・返金・AML/KYCは未決定。
- 他言語・外部サービスはRustでの実装が仕様適合や運用上妥当でない場合に限り採用理由を記録する。

## 3. コンポーネント境界

1. **Client**: 表示と操作を担う。クライアントからの入力・検証結果を信頼せず、サーバーで重要な不変条件を再検証する。
2. **API/Application**: Axum上のユースケース、JWT認可、本人確認の検証、モデレーション、決済・監査連携を提供する。
3. **Domain/Common**: コンテンツ、利用資格、取引、モデレーション、監査の規則を外部サービスから分離する。
4. **Adapters**: JPKI/マイナアプリ連携、libSQL、IPFS、監査アンカー、JPYC対応チェーン等を交換可能な境界として扱う。
5. **Distribution**: IPFS等の複数経路とキャッシュを検討し、可用性・遮断耐性・削除要請対応を併せて設計する。

## 4. 信頼モデル

- JPKI認証の有効性は、信頼されたアプリ・発行元・提示検証・nonce結合・失効確認のサーバー側検証に依存する。X.509から公開鍵を抽出するだけでは足りない。目標方式は
  [ADR-0002](adr/ADR-0002-jpki-authentication.md) を参照。
- JPYC取引は署名付き送金記録、チェーン、トークンコントラクト、最終性確認を検証して初めて成立扱いできる。DBの模擬ハッシュは支払証明ではない。目標方式は
  [ADR-0003](adr/ADR-0003-jpyc-settlement.md) を参照。
- 監査ログは第三者が再検証できる形式・鍵・公開範囲・保存経路が必要。DB単体のハッシュ連鎖は最終要件を満たさない。
- `CID` はコンテンツ参照、`SHA-256` はアプリケーション層で登録データとのバイト一致を確認する値であり、本人性や権利を証明しない。
- ハッシュ化した利用者識別子も個人情報性・相関可能性が残り得るため、匿名性を保証しない。

## 5. 主要データフロー

### 認証

1. サーバーが一意なチャレンジと検証要求を生成する。
2. 利用者は指定マイナアプリで認証し、提示を返す。
3. サーバーは信頼元・署名・nonce・audience・失効・必要属性を検証する。
4. 有効な認証結果に限り短寿命トークンを発行し、保護APIごとに認可する。

具体プロトコルは公式仕様・提供APIに基づき決定する。現行実装はこのフローを満たさない。

### 投稿・配信

投稿時に実データ形式・サイズ・署名を検証し、CIDとチェックサムを記録する。閲覧時は取得元を制限し、サイズ・チェックサム・MIMEを検証後に配信する。高速性のためキャッシュと複数配信経路を設計する。
反検閲性とコンテンツ削除・法的要請への対応を両立させる。

### モデレーション・監査

通報、暫定非表示、投票、判定、異議申立てを明示的な状態機械として管理する。重要イベントを署名・連鎖・外部検証可能な監査形式で記録する。個人情報を公開ログへ直接記録しない。

### JPYC取引

取引要求、ウォレット署名、チェーン送信、トランザクション確認、失敗・再試行・返金状態を区別する。JPYCの対応チェーン・最終性・手数料基準を確定するまでは模擬記録を実決済として扱わない。

## 6. クロスプラットフォーム性

- 対象OS・端末・ブラウザと最小バージョンを利用者層から決め、対応マトリクスを維持する。
- JXLデコード、Wasm機能、ファイル選択、JPKIアプリへの遷移・復帰、ウォレット接続を実機で確認する。
- 非対応環境では理由を明示し、プレビュー形式や表示のみ等の安全な代替を検討する。本人確認・決済の必須条件をスキップする代替は認めない。
- レスポンシブ表示、キーボード・支援技術による操作性も対象環境で検証する。

## 7. 性能・軽量性・費用

初期表示時間、APIレイテンシ、転送量、Wasmバンドルサイズ、IPFS解決時間、稼働費、JPYC送金手数料を計測対象とする。SLOと受入値は対象端末・ネットワーク・地域を指定して別途決定する。

## 8. 現行プロトタイプとの差分

現行コードはRust/Axum、Leptos、libSQL、Pinata/IPFSを用いるが、JPKI実認証、JPYC送金・検証、外部検証可能な監査、複数事業者による分散運用は完成していない。
開発モックは本番の利用資格判定・決済に使用しない。
