# 基本設計書 (Basic Design Document)

本ドキュメントは、要件定義書に基づき、システムを具体的に構成するための論理設計を定義する。

## 1. コンテンツスコープ

本プラットフォームで取り扱うコンテンツは以下の2種に限定する。

* **イラスト**: JPEG XL (.jxl) 形式の静止画。
* **小説**: Markdown (.md) 形式のテキストコンテンツ。
※ 動画、アニメーション、うごイラは完全に排除し、静的なデータ構造のみを維持する。

## 2. 技術スタックの確定

* **バックエンド**: Rust (Axum, workers-rs, Wasm)
* **データベース**: Turso (libSQL: 分散型 SQLite)
* **フロントエンド**: SolidJS + TypeScript
* **スタイリング**: Tailwind CSS (Zero-JS 最適化)
* **配信・ホスティング**: IPFS / Arweave
* **インフラ管理**: OpenTofu (HCL)

## 3. システム論理構成

### 3.1. データモデル

* **User**: ユーザー認証ハッシュ（JPKI由来）のみを保持。生の個人情報は保持しない。
* **Content**: イラストと小説のメタデータを統合管理。
  * `type`: "Illustration" | "Novel"
  * `cid`: コンテンツのアドレス (IPFS CID)
  * `owner_id`: ユーザーハッシュ
  * `checksum`: 完全性検証用ハッシュ値
* **Governance**: 陪審制投票ログ（投票者ハッシュ、判定結果、法的根拠）

### 3.2. 通信プロセス

1. **検証ゲート**: ユーザーは JPKI 署名を用いてリクエストを行う。Rust バックエンドにて署名検証・年齢確認を行う。
2. **データ取得**: バックエンドはメタデータを Turso から取得し、IPFS 上のコンテンツのアドレス (CID) をフロントエンドへ渡す。
3. **描画検証**: フロントエンド側で Wasm を用いて CID とコンテンツハッシュを照合し、Verified ステータスを点灯させる。

## 4. 真正性・完全性の保証プロセス

全てのコンテンツはアップロード時に SHA-256 ハッシュ値を計算し、Turso に記録する。フロントエンド側で動く Rust/Wasm モジュールが、IPFS から取得した実データから再度ハッシュを算出し、Turso にあるハッシュ値と一致しない場合、データの改ざん（またはダウンロード失敗）と判断する。

## 5. モデレーション論理

* 違法コンテンツ報告発生時、`Status` を `Reported` に変更し、一時非表示とする。
* ガバナンス・スマートコントラクトを介して陪審員投票を開始し、結果に基づいて `Approved` または `Rejected` を更新する。
* 最終的な `Rejected` (法的違反確定) 時、該当ユーザーの JPKI ハッシュを `Banned` テーブルへ移行し、アカウントを永久停止する。
